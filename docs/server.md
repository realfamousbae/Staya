# Сервер Staya

Решения по VPS и сервисам на нём. Задача 1.1 в `docs/PLAN.md`.

## Машина

- Play2Go LC-1, Финляндия: 1 vCPU, 2 ГБ RAM, 40 ГБ, Ubuntu 24.04, IP `2.27.42.60`.
- Имя: `2-27-42-60.sslip.io` (sslip.io отвечает адресом, записанным в имени). Свой домен не покупаем. Следствие: смена IP в панели меняет и имя — нужна новая сборка приложения.
- Приложения подключаются к серверу по IP, а имя используют только для TLS: так работа не зависит от DNS sslip.io (проверить реализацию на iOS — см. «Проверить по ходу» в PLAN).

## Доступ

- Администрирование: `ssh -i ~/.ssh/staya_vps staya@2.27.42.60` — пользователь `staya`, только ключ, `sudo` без пароля.
- Вход под `root` и вход по паролю **не меняются** — указание владельца сервера. Скрипты их не трогают.
- Через VPN-туннели новые соединения иногда обрываются — скрипты используют повторы и одно постоянное SSH-соединение.

## Настройка и деплой

- `deploy/setup-server.sh` — идемпотентная базовая настройка: sysctl, ufw, автообновления, Docker с ротацией логов, пользователь `staya`, каталоги и токен сборщика.
- `deploy/deploy.sh [сервис ...]` — с Mac: запускает настройку, копирует `docker-compose.yml` и `Caddyfile` в `/srv/staya`, обновляет образы и перезапускает сервисы.
- Образы собирает GitHub Actions (`.github/workflows/images.yml`) и публикует в `ghcr.io/realfamousbae/*`. На VPS ничего не компилируется. Пакеты в GHCR публичные (наследуют видимость репозитория), сервер скачивает их без токена. Исходящие соединения с VPS к GitHub иногда сбоят — `deploy.sh` повторяет скачивание.

## Сеть

- Клиенты за VPN: туннели режут ICMP, поиск MTU ломается, и большие пакеты (ответ на обмен ключами SSH, TLS ServerHello с сертификатом) теряются. Поэтому `net.ipv4.tcp_mtu_probing = 1` и `tcp_base_mss = 1024` (`/etc/sysctl.d/90-staya-net.conf`).
- Эти настройки действуют в сетевом пространстве хоста, поэтому Caddy работает с `network_mode: host`. Проверка: `curl https://2-27-42-60.sslip.io/mtu-test` (64 КБ) через туннель.
- ufw: входящие только 22, 80, 443/tcp. Docker обходит ufw для опубликованных портов, поэтому наружу публикует только Caddy, остальные сервисы — на `127.0.0.1`. Проверять снаружи, а не по `ufw status`.
- HTTP/3 выключен (`protocols h1 h2`): туннели хуже переносят QUIC, а 443/udp закрыт.

## TLS

- Caddy получает сертификат Let's Encrypt автоматически. Новый домен — сначала тестовый CA (по умолчанию в `docker-compose.yml`), боевой — `ACME_CA` в `/srv/staya/.env` после успешной проверки.
- ACME email не указывается: репозиторий публичный.
- Сертификаты — в томе `caddy_data`, переживают передеплой.
- Только TLS 1.3.

## Логи и данные

- Access-логов Caddy нет; IP клиентов нигде не пишутся. Сборщик метрик не читает `X-Forwarded-For`.
- Логи контейнеров ротируются: 3 × 10 МБ.

## Сборщик метрик этапа 1 (`tools/probe-server`)

- `POST /probe` с `Authorization: Bearer <токен>`; запись — строка JSON в `/srv/staya/probe-data/probe-day<N>.jsonl`.
- Схема строгая (`deny_unknown_fields`): поля — ID установки, платформа, стратегия, время, триггер, состояние приложения, точность в метрах, скорость корзинами, заряд, зарядка, режим энергосбережения, задержка и сбои прошлой отправки, разрешение на геолокацию и её точность (точная/примерная), фоновое обновление, число событий с прошлой отправки (отправки ограничены по частоте). Триггеры `continuous_start`/`continuous_stop` отмечают переключения адаптивной стратегии. **Координат в схеме нет**; запрос с лишними полями отклоняется.
- Токен генерируется на сервере (`/srv/staya/probe.env`, права 600), в git и в сборки приложения не попадает. В прототип вводится вручную на отладочном экране и хранится в Keychain/Keystore. Посмотреть: `ssh ... staya@2.27.42.60 'cat /srv/staya/probe.env'`.
- Выгрузки по HTTP нет. Каталог данных принадлежит пользователю контейнера (uid 65532, права 700), поэтому забирать через `sudo`:
  `ssh -i ~/.ssh/staya_vps staya@2.27.42.60 'sudo tar -C /srv/staya/probe-data -cz .' > probe-data.tgz`
- Хранение: данные удаляются с сервера после отчёта `docs/measurements/stage1.md` (задача 1.5).
