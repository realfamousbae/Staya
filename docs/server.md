# Сервер Staya

Решения по VPS и сервисам на нём. Задача 1.1 в `docs/PLAN.md`.

## Машина

- Play2Go LC-1, Финляндия: 1 vCPU, 2 ГБ RAM, 40 ГБ, Ubuntu 24.04.
- Имя: `<ip-через-дефисы>.sslip.io` (sslip.io отвечает адресом, записанным в имени). Свой домен не покупаем. Следствие: смена IP в панели меняет и имя — нужна новая сборка приложения.
- Приложения подключаются к серверу по IP, а имя используют только для TLS: так работа не зависит от DNS sslip.io (проверить реализацию на iOS — см. «Проверить по ходу» в PLAN).

## Доступ

- Администрирование: по SSH пользователем `staya`, только ключ, `sudo` без пароля. Адрес сервера в репозитории не хранится.
- Вход под `root` и вход по паролю **не меняются** — указание владельца сервера. Скрипты их не трогают.
- Через VPN-туннели новые соединения иногда обрываются — скрипты используют повторы и одно постоянное SSH-соединение.

## Настройка и деплой

- `deploy/setup-server.sh` — идемпотентная базовая настройка: sysctl, ufw, автообновления, Docker с ротацией логов, пользователь `staya`, каталоги и токен сборщика.
- `deploy/deploy.sh [сервис ...]` — с Mac, адрес и имя сервера — только из окружения (`STAYA_HOST`, `STAYA_DOMAIN`): запускает настройку, копирует `docker-compose.yml` и `Caddyfile` в `/srv/staya`, записывает имя в `/srv/staya/.env`, обновляет образы и перезапускает сервисы.
- Секреты генерирует `setup-server.sh` на самом сервере и они его не покидают: `probe.env` (токен сборщика), `postgres.env` (пароль базы), `server.env` (адрес базы и код приглашения на регистрацию). Права 600.
- Образы собирает GitHub Actions (`.github/workflows/images.yml`) и публикует в `ghcr.io/realfamousbae/*`. На VPS ничего не компилируется. Пакеты в GHCR публичные (наследуют видимость репозитория), сервер скачивает их без токена. Исходящие соединения с VPS к GitHub иногда сбоят — `deploy.sh` повторяет скачивание.

## Сеть

- Клиенты за VPN: туннели режут ICMP, поиск MTU ломается, и большие пакеты (ответ на обмен ключами SSH, TLS ServerHello с сертификатом) теряются. Поэтому `net.ipv4.tcp_mtu_probing = 1` и `tcp_base_mss = 1024` (`/etc/sysctl.d/90-staya-net.conf`).
- У самого VPS путь к интернету тоже меньше 1500 байт, и ICMP до него не доходит: соединения с внешними серверами (ghcr.io, Docker Hub) обрывались на TLS-рукопожатии в 25–33% попыток. Служба `staya-mtu` ставит MTU 1400 на основном интерфейсе при загрузке; после этого сбоев 0 из 30. Netplan не меняем — ошибка в нём отрезала бы сервер от сети.
- Эти настройки действуют в сетевом пространстве хоста, поэтому Caddy работает с `network_mode: host`. Проверка: `curl https://<имя сервера>/mtu-test` (64 КБ) через туннель.
- ufw: входящие только 22, 80, 443/tcp. Docker обходит ufw для опубликованных портов, поэтому наружу публикует только Caddy, остальные сервисы — на `127.0.0.1`. Проверять снаружи, а не по `ufw status`.
- HTTP/3 выключен (`protocols h1 h2`): туннели хуже переносят QUIC, а 443/udp закрыт.

## TLS

- Caddy получает сертификат Let's Encrypt автоматически. Новый домен — сначала тестовый CA (по умолчанию в `docker-compose.yml`), боевой — `ACME_CA` в `/srv/staya/.env` после успешной проверки.
- ACME email не указывается: репозиторий публичный.
- Сертификаты — в томе `caddy_data`, переживают передеплой.
- Только TLS 1.3.

## Логи и данные

- Access-логов Caddy нет; IP клиентов нигде не пишутся. Сборщик метрик не читает `X-Forwarded-For`.
- Логи контейнеров ротируются: 3 × 10 МБ.

## Сервер Staya (`server/`, этап 3)

- Сервисы: `server` (образ `ghcr.io/realfamousbae/staya-server`, только loopback-порт для Caddy, read-only, без capabilities) и `postgres` (18, только во внутренней сети `backend`, том `postgres_data`). Caddy проксирует `/v1/*`, включая WebSocket.

- Настройки — только переменные окружения: `STAYA_DATABASE_URL` и `STAYA_DOMAIN` (обязательны; домен — имя сервера в подписи входа, protocol §4.2), `STAYA_INVITE_CODE` (код приглашения на регистрацию; без него регистрация открыта — в журнал пишется предупреждение), `STAYA_LISTEN` (по умолчанию `127.0.0.1:8080`), `STAYA_LOG` (`info`).
- Вход: подписи проверяются `ed25519-dalek` (`verify_strict`); в базе только SHA-256 токенов; просроченные challenge и сессии удаляются раз в 10 минут.
- Миграции вшиты в бинарник (`server/migrations`, список в `server/src/db.rs`) и применяются при старте одной транзакцией под advisory-блокировкой. Сервер со схемой новее своей не стартует.
- Журнал запросов: метод, шаблон маршрута (`/v1/slots/{recipient}`, а не путь с ID), код, время. Никаких IP, заголовков, тел, параметров — это проверяет тест `server/tests/request_log.rs`. Ошибки базы в обработчиках не логировать текстом: в них бывают значения ключей.
- Остановка по SIGTERM (`docker stop`) с дожиданием запросов.
- Лимиты частоты (`server/src/ratelimit.rs`): любой запрос — 300 сразу и 10/с с одного IP; регистрация и вход — 20 сразу и 1 в 5 с с одного IP; запросы одной сессии — 120 сразу и 2/с. Сверх — `429`. IP используется только как ключ корзины в памяти, хешированный со случайной солью процесса; корзина забывается, когда снова полна. За Caddy включить `STAYA_TRUST_PROXY=1` — IP берётся из последнего адреса `X-Forwarded-For`; без прокси заголовок не учитывается (его подделывает клиент).
- `GET /health` — 200 или 503, без текста ошибки.
- Журнал самого PostgreSQL: в строках `DETAIL` ошибок он пишет значения ключей (ID аккаунтов), поэтому в compose `log_error_verbosity=terse`, `log_min_error_statement=panic`, подключения не логируются. Порт базы не публикуется, TLS к ней не нужен (внутренняя сеть Compose).
- Потеря базы не страшна: клиенты перерегистрируются (тот же ID и ключи) и заново публикуют ключи; теряются только недоставленные сообщения.

## Сборщик метрик этапа 1 (`tools/probe-server`)

- `POST /probe` с `Authorization: Bearer <токен>`; запись — строка JSON в `/srv/staya/probe-data/probe-day<N>.jsonl`.
- Схема строгая (`deny_unknown_fields`): поля — ID установки, платформа, стратегия, время, триггер, состояние приложения, точность в метрах, скорость корзинами, заряд, зарядка, режим энергосбережения, задержка и сбои прошлой отправки, разрешение на геолокацию и её точность (точная/примерная), фоновое обновление, число событий с прошлой отправки (отправки ограничены по частоте). Триггеры `continuous_start`/`continuous_stop` отмечают переключения адаптивной стратегии. Поля Android (необязательные, у iOS — `null`): исключение из оптимизации батареи, фоновое ограничение, корзина App Standby, Doze, реально использованный провайдер, наличие датчика значимого движения. **Координат в схеме нет**; запрос с лишними полями отклоняется.
- Токен генерируется на сервере (`/srv/staya/probe.env`, права 600), в git и в сборки приложения не попадает. В прототип вводится вручную на отладочном экране и хранится в Keychain/Keystore. Посмотреть — на сервере: `sudo cat /srv/staya/probe.env`.
- Выгрузки по HTTP нет. Каталог данных принадлежит пользователю контейнера (uid 65532, права 700), поэтому забирать через `sudo`:
  на сервере `sudo tar -C /srv/staya/probe-data -cz .` (архив данных сборщика).
- Хранение: данные удаляются с сервера после отчёта `docs/measurements/stage1.md` (задача 1.5).

## Карта (задача 3.9)

- Регион: Москва и Московская область (`35.10,54.20,40.25,57.00`), масштаб до 15, ~600 МБ. Данные — OpenStreetMap (ODbL) в схеме Protomaps.
- `deploy/update-map.sh` (с Mac, `STAYA_HOST`, `STAYA_DOMAIN`): копирует стили на сервер и там скачивает только тайлы региона из свежей сборки `build.protomaps.com`, шрифты и спрайты из `protomaps/basemaps-assets` (закреплённый коммит), подставляет адрес сервера в стили и перезапускает сервис `tiles`. Старая карта отдаётся, пока новая не готова. Запускать при первом деплое и по желанию раз в несколько месяцев.
- Раздача: `/tiles/region.json` (TileJSON) и `/tiles/region/{z}/{x}/{y}.mvt` — `go-pmtiles serve`; `/map/style-light.json`, `/map/style-dark.json`, `/map/fonts/...`, `/map/sprites/...` — файлы Caddy.
- Стили генерируются `tools/map-style` (`npm ci && npm run generate`) из `@protomaps/basemaps` с русскими подписями; результат лежит в `deploy/map`.
- Какие участки карты смотрит клиент, видит только наш сервер; журналов запросов нет. Ни приложение, ни карта не обращаются к сторонним серверам.

## Закрепление ключа (задача 3.10, protocol §5.3)

- Caddy с `reuse_private_keys`: ключ TLS не меняется при продлении сертификата, поэтому его отпечаток можно закрепить в приложениях и приглашениях. Опция помечена в документации Caddy как нерекомендуемая и может исчезнуть — на этот случай и есть запасной ключ.
- `deploy/pin.sh` — отпечаток ключа, который сервер предъявляет сейчас (`STAYA_DOMAIN`), или ключа из файла.
- `deploy/backup-key.sh` — один раз создаёт запасной ключ P-256 на своём компьютере и печатает его отпечаток. Ключ переносится в менеджер паролей, файл удаляется. На сервер и в репозиторий он не попадает.
- В приглашениях и в настройках приложения по умолчанию — оба отпечатка: `p=<основной>.<запасной>`.
- **Смена ключа** (компрометация, переезд, отказ от `reuse_private_keys`):
  1. Достать запасной ключ из менеджера паролей.
  2. Получить на него сертификат внешним ACME-клиентом с переиспользованием ключа (например, `lego --key-type ec256` с готовым ключом) и подключить в Caddy через `tls <cert> <key>`.
  3. Клиенты продолжают работать: запасной отпечаток они знают заранее.
  4. Создать новый запасной ключ; в новых приглашениях — оба актуальных отпечатка. Старые приглашения со старым основным отпечатком по-прежнему годятся, пока в них есть действующий запасной.
- Отпечатки публичны, но вместе с именем сервера в репозиторий их не кладём (публичный репозиторий без деталей сервера).
