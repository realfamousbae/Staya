# Протокол Staya

Статус: **v0.1** (задача 2.1). Эта версия — контракт для кода ядра и сервера: форматы байтов, размеры и числа ниже реализуются как есть. Любое изменение сначала вносится сюда, потом в код; несовместимые изменения повышают байт версии соответствующей структуры.

Ключевые слова «ДОЛЖЕН», «НЕ ДОЛЖЕН», «МОЖЕТ» — в смысле RFC 2119. Все многобайтовые целые — big-endian. `‖` — конкатенация.

## 1. Цели

1. Сервер не узнаёт координаты, даже при полном доступе к базе и трафику.
2. Получатель всегда может расшифровать **последний** пакет отправителя, сколько бы пакетов он ни пропустил.
3. Отзыв доступа мгновенный: после удаления друга он не получает ни одного нового пакета.
4. Разная точность для разных друзей без отдельных механизмов: у каждого друга свой канал.
5. Никакой собственной криптографии: только vodozemac (Olm, Megolm) и проверенные примитивы RustCrypto.

## 2. Криптографическая основа

| Задача | Механизм |
| --- | --- |
| Идентичность устройства | `vodozemac::olm::Account`: Curve25519 `ik` + Ed25519 `sk` |
| Попарный канал для управляющих сообщений | Olm, `olm::SessionConfig::version_1()` |
| Канал позиций к одному другу | Megolm, `megolm::SessionConfig::version_1()`, отдельная исходящая `GroupSession` на каждого друга |
| Аутентификация на сервере | Подпись Ed25519 challenge (§4) |
| Шифрование локальной базы | Зашифрованные pickle vodozemac + `chacha20poly1305` |

Версия vodozemac: 0.11. Feature `experimental-session-config` НЕ ДОЛЖНА включаться: версии 2 Olm и Megolm за ней не стандартизированы.

### 2.1. Почему не Olm на каждый пакет

В Olm vodozemac действует `MAX_MESSAGE_GAP = 2000`: при пропуске больше 2000 шагов цепочки расшифровка возвращает `TooBigMessageGap`. Сервер хранит только последний пакет позиции, поэтому при отправке раз в минуту получатель терял бы канал за полтора дня офлайна. У Megolm `InboundGroupSession` лимита нет: ratchet перематывается к любому индексу. Olm используется только для редких управляющих сообщений, которые доставляются очередью без пропусков.

## 3. Идентификаторы и ключи

| Сущность | Размер | Описание |
| --- | --- | --- |
| `account_id` | 16 байт | Случайный, генерируется на устройстве. Не выводится из ключей |
| `ik` | 32 байта | Curve25519 identity key |
| `sk` | 32 байта | Ed25519 identity key |
| OTK | 32 байта | Curve25519 one-time key; публикуется с подписью (§4.3) |
| Fallback-ключ | 32 байта | Curve25519; используется, когда OTK закончились |
| Ключ локальной базы | 32 байта | iOS Keychain (`AfterFirstUnlockThisDeviceOnly`); Android — обёрнут AES-GCM-ключом Keystore |

- Клиент поддерживает на сервере **50** OTK и пополняет до 50, когда осталось **меньше 20**.
- Fallback-ключ ротируется раз в **7 дней**; предыдущий хранится ещё 7 дней для запоздавших PreKey-сообщений.
- Приватные ключи НЕ ДОЛЖНЫ покидать устройство ни в каком виде.

## 4. Подписи ключом `sk`

Все подписи — Ed25519 ключом `sk`. Каждое назначение имеет свою строку-контекст, оканчивающуюся нулевым байтом, так что ни одна подписанная строка не может быть префиксом другой. После контекста идут только поля фиксированной длины или с префиксом длины.

| Назначение | Подписываемые байты |
| --- | --- |
| Регистрация | `"staya/v1/register\0"` ‖ `account_id`[16] ‖ `ik`[32] ‖ `sk`[32] |
| Вход | `"staya/v1/auth\0"` ‖ `len(domain)`[u8] ‖ `domain` (ASCII) ‖ `nonce`[32] ‖ `account_id`[16] |
| OTK | `"staya/v1/otk\0"` ‖ `otk`[32] |
| Fallback-ключ | `"staya/v1/fallback\0"` ‖ `fallback`[32] |

### 4.1. Регистрация

`POST /v1/accounts` с `account_id`, `ik`, `sk`, подписью регистрации и кодом приглашения на сервер (только на время беты). Повторная регистрация с теми же `account_id` и ключами идемпотентна: если база сервера потеряна, клиент перерегистрируется автоматически.

### 4.2. Вход

1. `POST /v1/auth/challenge {account_id}` → `nonce` (32 случайных байта, одноразовый, живёт 60 с).
2. Клиент подписывает строку входа; `domain` — хост сервера, которому клиент подключается.
3. `POST /v1/auth/verify` → токен сессии (32 случайных байта). Сервер хранит только SHA-256 токена, срок жизни — **30 дней**.

### 4.3. Одноразовые ключи

При `claim` получатель ДОЛЖЕН проверить подпись OTK или fallback-ключа ключом `sk`, полученным вне сервера (из QR или ссылки), и отвергнуть неподписанный ключ.

## 5. Добавление друга

A приглашает, B принимает приглашение.

1. A создаёт одноразовый **токен приглашения** `t` (16 случайных байт). Срок жизни: **10 минут** для QR, **24 часа** для ссылки. Токен хранится только на устройстве A.
2. A показывает QR или ссылку. Поля в base64url без выравнивания:
   `staya://add?v=1&id=<account_id>&ik=<ik>&sk=<sk>&t=<t>&m=<q|l>`, где `m` — способ (`q` — QR, `l` — ссылка).
3. B забирает у сервера OTK A (или fallback-ключ), проверяет подпись (§4.3) и создаёт исходящую Olm-сессию на `ik` A.
4. B отправляет `FriendRequest` (§6) со своими `account_id`, `sk`, токеном `t`, ключом Megolm B→A и профилем.
5. A расшифровывает PreKey-сообщение, проверяет:
   - `t` совпадает с неиспользованным неистёкшим токеном — иначе сообщение отбрасывается;
   - `account_id` из сообщения совпадает с отправителем, указанным сервером;
   - Curve25519-ключ из PreKey-сообщения — это `ik` B.
   После этого A погашает токен и отвечает `FriendAccept` с ключом Megolm A→B и профилем.

### 5.1. Статус проверки

- `m=q` (QR при встрече) → «проверено»: ключи A пришли по физическому каналу, токен знал только тот, кто видел QR.
- `m=l` (ссылка) → «не проверено», пока оба не сверят код безопасности.

### 5.2. Код безопасности

Как численный отпечаток Signal (NumericFingerprint v2):

1. Отпечаток стороны: `h = SHA-512("staya/v1/fingerprint\0" ‖ ik ‖ sk ‖ account_id)`, затем 5199 раз `h = SHA-512(h ‖ ik ‖ sk)`. Берутся первые 30 байт.
2. 30 байт → 6 групп по 5 байт; каждая группа — 40-битное число, `mod 100000`, дополняется нулями слева до 5 цифр. Итого 30 цифр.
3. Код безопасности — 30 цифр стороны с меньшим `account_id` (побайтово), затем 30 цифр другой стороны: 60 цифр, показываются группами по 5.

## 6. Управляющие сообщения (Olm)

### 6.1. Открытый текст

```
version  u8   = 1
type     u8
body     ...  (по таблице ниже)
padding       нули до размера корзины
```

| type | Имя | body |
| --- | --- | --- |
| 1 | `FriendRequest` | `token`[16] ‖ `account_id`[16] ‖ `sk`[32] ‖ `session_key` (lp16) ‖ `profile` |
| 2 | `FriendAccept` | `session_key` (lp16) ‖ `profile` |
| 3 | `SessionShare` | `session_key` (lp16) |
| 4 | `Profile` | `profile` |
| 5 | `Unfriend` | пусто |

- `lp16` — длина `u16`, затем байты. `session_key` — `megolm::SessionKey::to_bytes()` (229 байт в version 1).
- `profile` = `nick` (длина `u8`, UTF-8, ≤ 64 байт) ‖ `avatar` (длина `u16`, JPEG ≤ 8192 байт; 0 — нет аватара).
- Паддинг ДОЛЖЕН быть нулями; получатель разбирает body по длинам и игнорирует остаток. Неизвестный `version` или `type` — сообщение отбрасывается.

### 6.2. Корзины и конверт

Открытый текст дополняется до наименьшей подходящей корзины: **256**, **1024** или **9216** байт. Шифротекст Olm упаковывается в конверт фиксированного размера:

| Корзина открытого текста | Размер конверта |
| --- | --- |
| 256 | 512 |
| 1024 | 1280 |
| 9216 | 9472 |

Конверт: `len`[u16] ‖ `olm_type`[u8] (0 — PreKey, 1 — Normal) ‖ байты Olm-сообщения ‖ нули до размера конверта. Запас в конверте покрывает заголовок Olm (ключ ratchet, счётчик varint и для PreKey — базовый ключ, OTK, `ik`). Максимальные размеры проверяются тестом в `staya-proto`.

### 6.3. Сессии Olm с одним другом

С одним другом может существовать несколько Olm-сессий (например, если оба одновременно добавили друг друга).

- Получатель хранит до **3** сессий на друга и при расшифровке пробует их от самой свежей к самой старой; при PreKey-сообщении, не подошедшем ни к одной, создаёт новую входящую сессию.
- Отправитель шифрует сессией, которая последней успешно **расшифровала** сообщение от этого друга, а если таких нет — самой свежей созданной.

## 7. Пакеты позиции (Megolm)

### 7.1. Открытый текст — ровно 48 байт

| Смещение | Поле | Тип | Примечание |
| --- | --- | --- | --- |
| 0 | version | u8 | = 1 |
| 1 | kind | u8 | 0 `Exact`, 1 `Approx`, 2 `Hidden`, 3 `Frozen` |
| 2 | lat | i32 | градусы × 10⁷; для `Hidden` — 0 |
| 6 | lon | i32 | градусы × 10⁷; для `Hidden` — 0 |
| 10 | accuracy | u16 | метры, насыщение на 65535 |
| 12 | timestamp | i64 | Unix-время замера, секунды |
| 20 | flags | u16 | резерв, = 0 |
| 22 | reserved | 26 байт | нули при отправке, игнорируются при приёме |

### 7.2. Конверт — ровно 160 байт

`len`[u16] ‖ `MegolmMessage::to_bytes()` ‖ нули до 160. Сообщение Megolm от 48 байт открытого текста занимает 141–145 байт в зависимости от длины varint-индекса. Session ID в конверте не передаётся.

### 7.3. Режимы

- **Exact** — позиция как есть.
- **Approx** — привязка к центру ячейки сетки. Шаг по широте — 0,01° (≈1,1 км). Шаг по долготе — `0,01° / cos(φ)`, где φ — широта центра ячейки, cos ограничен снизу 0,1. `accuracy` = половина диагонали ячейки. Случайный шум НЕ ДОЛЖЕН использоваться: его можно усреднить по многим пакетам.
- **Hidden** — «скрыто» для конкретного друга или глобальный режим призрака.
- **Frozen** — одна и та же зафиксированная позиция и её исходный `timestamp`.

### 7.4. Неразличимость режимов

- Пакеты всем друзьям уходят **одним пакетом конвертов**: друг с `Hidden` получает конверт в той же отправке, что и остальные, поэтому по трафику режим для конкретного друга не виден.
- Глобальный призрак и заморозка отправляют пакеты с частотой состояния покоя (**раз в 15 минут**; уточняется замерами этапа 1). Для сервера это выглядит как «стоит на месте» — утечка, уже принятая в модели угроз.

### 7.5. Ротация и проверки получателя

- Исходящая сессия к другу ротируется **раз в 24 часа или каждые 1000 пакетов** (что раньше), а также при удалении друга (сессия уничтожается). Новый ключ отправляется `SessionShare` **в той же отправке и раньше** первого пакета новой сессией.
- Получатель ДОЛЖЕН:
  1. атрибутировать пакет другу, чья входящая сессия его расшифровала; поле отправителя от сервера — только подсказка, какие сессии пробовать;
  2. после успешной расшифровки вызвать `advance_to(index)`;
  3. после первой успешной расшифровки пакетом новой сессии удалить предыдущую входящую сессию этого друга (защита от отката к старой сессии);
  4. отвергать пакет, у которого `timestamp` не больше последнего принятого от этого друга (защита от повтора);
  5. показывать время из `timestamp` пакета, а не время на сервере.
- Пакет с сессией, которой ещё нет у получателя, НЕ отбрасывается: он хранится до следующей выборки управляющих сообщений (WebSocket может поменять порядок доставки).

## 8. Сервер

### 8.1. Почтовые ящики

| Структура | Ключ | Семантика | Хранение |
| --- | --- | --- | --- |
| `location_slots` | (отправитель, получатель) | upsert: только последний конверт | **72 часа** с последнего обновления |
| `control_queue` | (получатель, порядковый номер) | очередь до ack | **30 дней** |

- Отправителя сервер ДОЛЖЕН брать из токена сессии, а не из тела запроса.
- Сервер принимает только конверты точных размеров (160 для позиций; 512, 1280, 9472 для управляющих) и больше ничего не знает об их содержимом.
- Лимит очереди: **200** управляющих сообщений на получателя; сверх лимита новые отвергаются.
- Управляющие сообщения НЕ ДОЛЖНЫ перезаписываться пакетами позиции.

### 8.2. Порядок обработки на клиенте

1. При каждой выборке клиент обрабатывает сначала `control_queue`, затем `location_slots`.
2. Подтверждение (`ack`) управляющего сообщения отправляется после того, как результат его обработки записан в локальную базу.
3. Отправка: один HTTP-запрос со всеми конвертами для всех друзей.
4. Получение: при открытии приложения и по WebSocket, пока приложение открыто. Пушей в MVP нет.

### 8.3. API (эскиз; JSON, конверты в base64)

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/v1/accounts` | регистрация (§4.1) |
| POST | `/v1/auth/challenge`, `/v1/auth/verify` | вход (§4.2) |
| PUT | `/v1/keys` | публикация OTK и fallback-ключа с подписями |
| POST | `/v1/keys/claim` | выдать один OTK (или fallback-ключ) аккаунта |
| GET | `/v1/keys/count` | сколько своих OTK осталось на сервере |
| POST | `/v1/envelopes` | пакет конвертов: `[{to, kind, data}]` |
| GET | `/v1/mailbox` | вся очередь и все слоты для меня |
| POST | `/v1/mailbox/ack` | подтвердить управляющие сообщения |
| DELETE | `/v1/slots/{recipient}` | удалить мой слот у получателя |
| GET | `/v1/ws` | WebSocket: новые конверты для меня |

Точные схемы запросов фиксируются в `staya-proto` (задача 2.2).

## 9. Удаление друга

1. Локально удаляются Olm- и Megolm-сессии с другом и все его данные.
2. Клиент удаляет свой слот в ящике бывшего друга (`DELETE /v1/slots/{id}`). Намерение сохраняется в локальной базе и повторяется, пока сервер не подтвердит удаление (в том числе после офлайна).
3. Отправка ему прекращается. Конверты от него, если продолжат приходить, игнорируются: сессий для расшифровки больше нет.
4. МОЖЕТ отправляться `Unfriend`, чтобы приложение друга убрало нас из списка.
