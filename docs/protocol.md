# Протокол Staya

Статус: **черновик v0** (этап 0.6). Полная спецификация с точными форматами байтов — задача 2.1, до написания кода ядра. Любое изменение протокола сначала вносится сюда, потом в код.

Ключевые слова «ДОЛЖЕН», «НЕ ДОЛЖЕН», «МОЖЕТ» — в смысле RFC 2119.

## 1. Цели

1. Сервер не узнаёт координаты, даже при полном доступе к базе и трафику.
2. Получатель всегда может расшифровать **последний** пакет отправителя, сколько бы пакетов он ни пропустил.
3. Отзыв доступа мгновенный: после удаления друга он не получает ни одного нового пакета.
4. Разная точность для разных друзей без отдельных механизмов: у каждого друга свой канал.
5. Никакой собственной криптографии: только vodozemac (Olm, Megolm) и проверенные примитивы RustCrypto.

## 2. Криптографическая основа

| Задача | Механизм |
| --- | --- |
| Идентичность устройства | `vodozemac::olm::Account`: Curve25519 (обмен ключами) + Ed25519 (подписи) |
| Попарный канал для управляющих сообщений | Olm (Double Ratchet) |
| Канал позиций к одному другу | Megolm: отдельная исходящая `GroupSession` на каждого друга |
| Аутентификация на сервере | Подпись Ed25519 случайного challenge |
| Шифрование локальной базы | Зашифрованные pickle vodozemac + `chacha20poly1305` |

### 2.1. Почему не Olm на каждый пакет

В Olm vodozemac действует `MAX_MESSAGE_GAP = 2000`: если между последним прочитанным и новым сообщением больше 2000 шагов цепочки, расшифровка возвращает `TooBigMessageGap`. Сервер хранит только последний пакет позиции, поэтому получатель, не открывавший приложение пару дней при отправке раз в минуту, потерял бы канал.

У Megolm `InboundGroupSession` такого лимита нет: получатель перематывает ratchet к любому индексу. Olm используется только для редких управляющих сообщений, которые доставляются очередью без пропусков.

## 3. Идентификаторы и ключи

- **ID аккаунта** — 128 случайных бит, генерируется на устройстве. Не выводится из ключей: это оставляет возможность сменить ключи (несколько устройств — «Позже»).
- **Ключи идентичности** — Curve25519 `ik` и Ed25519 `sk` из `olm::Account`.
- **Одноразовые ключи (OTK)** — Curve25519, подписанные `sk`. Клиент публикует ~50 штук и пополняет, когда на сервере осталось меньше 20.
- **Fallback-ключ** — используется, когда OTK закончились; ротируется клиентом.
- **Ключ локальной базы** — 32 случайных байта: iOS Keychain (`AfterFirstUnlockThisDeviceOnly`), Android — обёрнут AES-GCM-ключом Android Keystore.

Приватные ключи НЕ ДОЛЖНЫ покидать устройство ни в каком виде.

## 4. Аккаунт и аутентификация

1. Регистрация: `POST /v1/accounts` с `{id, ik, sk, подпись sk над (id, ik)}` и кодом приглашения на сервер (только на время беты). Повторная регистрация с теми же ключами идемпотентна: если база сервера потеряна, клиенты перерегистрируются автоматически.
2. Вход: `POST /v1/auth/challenge {id}` → `nonce`; клиент подписывает `"staya-auth-v1" ‖ домен сервера ‖ nonce` ключом `sk`; `POST /v1/auth/verify` → токен сессии. Сервер хранит только хеш токена, с TTL.

## 5. Добавление друга

A приглашает, B принимает приглашение.

1. A создаёт одноразовый **токен приглашения** `t` (128 бит, срок жизни: QR — минуты, ссылка — сутки). Токен хранится только на устройстве A.
2. A показывает QR или ссылку: `staya://add?v=1&id=<A.id>&ik=<A.ik>&sk=<A.sk>&t=<t>`.
3. B забирает OTK A с сервера (`claim`), **проверяет подпись OTK ключом `sk` из QR** и создаёт исходящую Olm-сессию.
4. B отправляет A управляющее сообщение `FriendRequest { t, профиль B, ключ Megolm B→A }`.
5. A расшифровывает сообщение, проверяет, что `t` совпадает с неиспользованным токеном, погашает токен и отвечает `FriendAccept { профиль A, ключ Megolm A→B }`.

Статус проверки:

- QR при встрече — «проверено»: ключи A пришли по физическому каналу, а токен знал только тот, кто видел QR.
- Ссылка — «не проверено», пока оба не сверят **код безопасности**: хеш от упорядоченной пары ключей идентичности `(ik, sk)` обоих, показанный как цифры (формат — в v0.1).

## 6. Управляющие сообщения (Olm)

Все передаются через попарную Olm-сессию и лежат на сервере в очереди `control_queue` до подтверждения получения.

| Тип | Содержимое | Когда |
| --- | --- | --- |
| `FriendRequest` | токен, профиль, ключ Megolm | при добавлении |
| `FriendAccept` | профиль, ключ Megolm | ответ на запрос |
| `SessionShare` | новый ключ Megolm (ротация) | раз в сутки или каждые N пакетов |
| `Profile` | ник, аватар (JPEG ≤ 8 КБ) | при изменении |
| `Unfriend` | — | МОЖЕТ отправляться при удалении |

Управляющие сообщения дополняются до одного из фиксированных размеров (корзины; значения — в v0.1).

## 7. Пакеты позиции (Megolm)

### 7.1. Содержимое

Бинарный формат фиксированной длины, до шифрования:

| Поле | Тип | Примечание |
| --- | --- | --- |
| версия | u8 | |
| тип | u8 | `Exact`, `Approx`, `Hidden`, `Frozen` |
| широта, долгота | i32 × 2 | градусы × 10⁷; для `Hidden` — нули |
| точность | u16 | метры |
| время | i64 | Unix-время замера, секунды |
| флаги | u16 | резерв |
| дополнение | | до фиксированного размера |

Все типы шифруются в пакет **одного размера**: сервер не отличает точную позицию от режима призрака.

### 7.2. Режимы

- **Exact** — позиция как есть.
- **Approx** — позиция привязывается к центру ячейки фиксированной сетки (~1 км). Случайный шум НЕ ДОЛЖЕН использоваться: его можно усреднить по многим пакетам. Цена сетки — видно, когда человек пересекает границу ячейки; это записано в модели угроз.
- **Hidden** — режим призрака или «скрыто» для конкретного друга. Пакеты продолжают уходить (реже), чтобы по трафику нельзя было понять, что включён призрак.
- **Frozen** — отправляется одна и та же зафиксированная позиция.

### 7.3. Шифрование и ротация

- Для каждого друга своя исходящая Megolm `GroupSession`; её ключ передаётся через `SessionShare` / `FriendRequest` / `FriendAccept`.
- Ротация: раз в сутки или каждые N пакетов (N — в v0.1), а также при удалении друга (сессия просто уничтожается).
- Получатель после успешной расшифровки ДОЛЖЕН вызвать `advance_to(index)`, чтобы старые пакеты стало невозможно расшифровать с его устройства.
- Пакет подписан Ed25519-ключом сессии; получатель принимает сессию, только если её ключ пришёл по Olm-каналу от этого друга.

## 8. Сервер: почтовые ящики

| Структура | Ключ | Семантика | Хранение |
| --- | --- | --- | --- |
| `location_slots` | (отправитель, получатель) | upsert: только последний пакет | TTL (значение — в v0.1) |
| `control_queue` | получатель, порядковый номер | очередь до ack | TTL 30 дней |

- Управляющие сообщения НЕ ДОЛЖНЫ перезаписываться пакетами позиции, иначе потеряется раздача ключа.
- Одна отправка — один HTTP-запрос со всеми конвертами для всех друзей: радио просыпается один раз.
- Сервер проверяет только фиксированные размеры конвертов и лимиты; содержимое для него непрозрачно.
- Получение: при открытии приложения (`GET` всех слотов и очереди) и по WebSocket, пока приложение открыто. Пушей в MVP нет.

## 9. Удаление друга

1. Локально удаляются Olm- и Megolm-сессии с другом и все его данные.
2. Клиент удаляет свой слот в ящике бывшего друга (`DELETE`), так что последняя позиция исчезает с сервера сразу.
3. Отправка ему прекращается. Пакеты от него, если продолжат приходить, игнорируются и удаляются.
4. МОЖЕТ отправляться `Unfriend`, чтобы приложение друга убрало нас из списка.

## 10. Открыто до v0.1 (задача 2.1)

- Точные байтовые форматы конвертов и размеры корзин дополнения.
- N для ротации Megolm и TTL слотов позиции.
- Формат кода безопасности (длина, группировка цифр).
- Шаг сетки для `Approx` и частота пакетов `Hidden`.
- Формат сериализации управляющих сообщений.
