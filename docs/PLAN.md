# Staya — план проекта

Создан 27.09.2026 · @Aleksey. Этот файл — единственный источник правды по плану: решения, этапы, чекбоксы задач.

## Обзор

Staya — открытое мобильное приложение для iOS и Android, чтобы делиться геопозицией с небольшим кругом друзей. Сервер при этом не видит координат. Первая аудитория — автор и около 10 друзей (примерно поровну iPhone и Android), публикация в сторах позже.

Принципы, по которым проверяется каждое решение:

- **Безопасность важнее функций.** Любая фича сначала сверяется с моделью угроз.
- **Сквозное шифрование.** Координаты расшифровываются только на устройствах получателей.
- **Минимум данных.** Без номера телефона и email, без истории перемещений — ни на сервере, ни на устройстве.
- **Независимость.** Свой сервер, открытые карты, открытый исходный код (AGPL-3.0).
- **Контроль у пользователя.** Режим призрака, своя точность для каждого друга, мгновенный отзыв доступа.

## Модель угроз

Исходим из того, что сервер может быть взломан или изъят. Даже с полным доступом к базе и трафику атакующий не должен узнать, где находятся пользователи. Подробности — в `docs/threat-model.md`.

| Угроза | Защита |
| --- | --- |
| Взлом или изъятие сервера | Сквозное шифрование; на сервере только шифротекст последнего пакета с ограниченным сроком хранения (TTL) |
| Перехват трафика | TLS 1.3 и certificate pinning поверх сквозного шифрования |
| Украденный телефон | Ключ локальной базы в Keychain (iOS) и Android Keystore, зашифрованная локальная база; биометрия — на этапе 5 |
| Бывший друг | Удаление из друзей уничтожает его Megolm-сессию и удаляет наш пакет из его ящика на сервере |
| Подмена ключа при добавлении друга (MITM) | Обмен через QR-код при встрече или сверка кода безопасности, как в Signal |
| Метаданные: кто с кем дружит и когда активен | Случайные идентификаторы без телефонов, пакеты одного размера, позже sealed sender |
| Утечка через пуши Apple и Google | В MVP пушей нет вовсе; позже — только пустые пуши «проснись и забери пакет» |
| Утечка через запросы карт | Тайлы, стиль, шрифты и спрайты со своего сервера |
| Цепочка поставок | Минимум зависимостей, никаких SDK аналитики и рекламы, `cargo deny`, воспроизводимые сборки |

Вне рамок проекта: взломанная ОС или root на устройстве, физическое принуждение, определение местоположения оператором связи.

Метаданные, которые сервер видит в MVP (осознанно): идентификаторы отправителя и получателя, время, тип конверта (управляющий или позиция), ритм отправки (движение или покой).

## Криптография

Своих алгоритмов не пишем. Библиотека — [vodozemac](https://github.com/matrix-org/vodozemac) (Rust, Olm/Megolm из Matrix, Apache-2.0, прошла аудит). libsignal отклонена: её README прямо говорит, что использование вне Signal не поддерживается.

**Почему Olm + Megolm, а не Olm на каждый пакет.** В Olm vodozemac есть лимит `MAX_MESSAGE_GAP = 2000`: если получатель пропустил больше 2000 сообщений, расшифровка падает с `TooBigMessageGap`. Сервер хранит только последний пакет, поэтому друг, не открывавший приложение пару дней, не смог бы прочитать ничего. У Megolm такого лимита нет, а `advance_to(index)` стирает старое состояние ratchet. Это стандартная схема Matrix.

- **Olm (попарно, редко):** управляющие сообщения — запрос и подтверждение дружбы, раздача ключа Megolm, профиль (ник и аватар), уведомление об удалении.
- **Megolm (на каждого друга, часто):** для каждого друга своя исходящая сессия, её ключ передаётся через Olm. Ротация раз в сутки или каждые N сообщений; при удалении друга сессия уничтожается. Получатель после расшифровки вызывает `advance_to`.

Разная точность для разных друзей и мгновенный отзыв получаются сами собой: у каждого друга своя сессия.

**Ключи и аккаунт.**

- Аккаунт — `vodozemac::olm::Account` (Curve25519 + Ed25519), созданный на устройстве. Приватные ключи никогда не покидают телефон. На сервере аккаунт — случайный 128-битный ID плюс публичные ключи.
- Сервер аутентифицирует клиента по подписи Ed25519 случайного challenge, без паролей.
- Состояние vodozemac хранится зашифрованными pickle в локальной базе; остальные записи шифруются `chacha20poly1305`. Ключ базы (32 случайных байта) — в Keychain с доступом `AfterFirstUnlockThisDeviceOnly` и под ключом Android Keystore. Режим «после первой разблокировки» нужен, потому что геопозиция отправляется в фоне при заблокированном экране.

**Добавление друга.**

1. A показывает QR или ссылку `staya://add?v=1&id=…&ik=…&sk=…&t=…`: идентификатор, ключи идентичности, одноразовый токен приглашения (хранится только на устройстве A).
2. B забирает с сервера одноразовый ключ A, проверяет его подпись ключом `sk` из QR и отправляет Olm-сообщение `FriendRequest` с токеном, своим ключом Megolm и профилем.
3. A проверяет токен и отвечает `FriendAccept`. Добавление по QR при встрече — «проверено», по ссылке — «не проверено», пока оба не сверят код безопасности.

**Пакет геопозиции.** Бинарный формат фиксированной длины: версия, тип, широта и долгота (1e-7°), точность, время, флаги. Типы: `Exact`, `Approx` (привязка к фиксированной сетке ~1 км, без случайного шума), `Hidden` (режим призрака или «скрыто» для друга), `Frozen`. Все типы одного размера — сервер их не различает. Все конверты для всех друзей отправляются одним запросом.

**Почтовый ящик на сервере — две структуры:**

- `location_slots (sender, recipient)` — только последний Megolm-пакет, перезаписывается, удаляется по TTL;
- `control_queue` — Olm-сообщения в очереди до подтверждения получения (TTL 30 дней). Их нельзя перезаписывать, иначе потеряется раздача ключа.

## Архитектура и стек

Нативные приложения на обеих платформах плюс общее ядро на Rust: фоновая геолокация и хранилища ключей требуют платформенного кода, а шифрование должно быть реализовано один раз.

Компоненты: приложение iOS и приложение Android (каждое — нативный UI, геолокация и сеть поверх общего Rust-ядра), сервер почтовых ящиков, сервер тайлов, PostgreSQL. Приложения шифруют координаты на устройстве; сервер хранит последний зашифрованный пакет и отдаёт его по запросу или по WebSocket.

Ядро работает без ввода-вывода (sans-IO): формирует конверты для отправки и разбирает входящие, а сетью занимается платформа — так фоновая сеть живёт по правилам ОС.

| Компонент | Выбор | Почему |
| --- | --- | --- |
| iOS | Swift, SwiftUI, CoreLocation, MapLibre Native; iOS 18+ | Полный контроль над фоновым режимом и Keychain |
| Android | Kotlin, Jetpack Compose, foreground service, LocationManager, MapLibre; minSdk 29, compileSdk/targetSdk 37 | Без Google Play Services |
| Общее ядро | Rust + UniFFI: vodozemac, протокол, локальное хранилище (rusqlite) | Одна реализация шифрования для двух платформ |
| Сервер | Rust (axum), WebSocket, PostgreSQL (tokio-postgres) | Тот же язык, что у ядра, минимум компонентов |
| Карты | OpenStreetMap, вырезка PMTiles города/области, `go-pmtiles serve` за Caddy | Запросы тайлов не раскрывают район третьей стороне |
| Пуши | В MVP нет. Позже APNs (нужен Apple Developer Program), на Android — UnifiedPush или FCM | Отправку на iOS будит CoreLocation, на Android — foreground service |
| Инфраструктура | VPS Play2Go (Германия), Docker Compose, Caddy, домен или deSEC | Дёшево, свой TLS и pinning; переезд тривиален |

Структура репозитория:

```
proto/        staya-proto: форматы конвертов, API-типы, константы размеров (без криптографии)
core/         staya-core: vodozemac, протокол, хранилище, UniFFI
core/fuzz/    cargo-fuzz
server/       staya-server: axum, tokio-postgres, WebSocket
tools/        probe-server (метрики этапа 1), uniffi-bindgen
ios/          Xcode-проект + Swift Package StayaCore (XCFramework)
android/      Gradle: :app, :core (jniLibs + Kotlin-привязки)
deploy/       docker-compose.yml, Caddyfile, скрипты тайлов и деплоя
scripts/      сборка ядра под iOS и Android
docs/         PLAN.md, protocol.md, threat-model.md, measurements/
```

## Функции

MVP — это минимум, при котором Staya уже можно пользоваться каждый день вместо других приложений.

**MVP**

- Аккаунт без телефона и email: ключи на устройстве, ник и аватар (передаются друзьям через E2E)
- Добавление друга по QR-коду или ссылке со сверкой кода безопасности
- Карта с друзьями: аватар, время последнего обновления, точность
- Фоновая отправка геопозиции с адаптивной частотой: реже в покое, чаще в движении
- Режим призрака и заморозка позиции
- Точность для каждого друга: точная, примерная (район) или скрыта
- Удаление друга с мгновенным отзывом доступа
- Без истории перемещений; при потере телефона друзья добавляются заново

**Следующий шаг**

- Заряд батареи и короткий статус
- «Пинг» друга: запрос свежей позиции (вместе с пушами)
- Места и уведомления «пришёл/ушёл». Геозоны считаются на устройстве получателя, сервер о местах не знает
- Блокировка приложения биометрией
- Sealed sender: сервер не знает отправителя пакета

**Позже**

- Несколько устройств на один аккаунт
- Дружба между разными серверами (федерация)
- Зашифрованная резервная копия ключей по паролю
- Групповые «стаи» на протоколе MLS, если друзей станет много
- Публикация в App Store, Google Play и RuStore, внешний аудит безопасности

Прямой обмен симулятор ↔ эмулятор в CI невозможен (разные раннеры: macOS и Linux с KVM), а локально их не ставим; совместимость — через общего собеседника на том же ядре. Отладочного экрана нет: обмен проверяется тестами

Готово, когда: iOS-симулятор и Android-эмулятор каждый обмениваются зашифрованными позициями с собеседником на ядре через dev-сервер (CI), все тесты и fuzz-цели зелёные.

### Этап 3. Сервер

- [x] 3.1 PostgreSQL 18 через `tokio-postgres` + `deadpool-postgres` (sqlx 0.9 несовместим с rusqlite ядра: обе тянут нативный SQLite, а в workspace может быть только одна копия); миграции вшиты в бинарник, применяются одной транзакцией под advisory-блокировкой, новее своей схемы сервер не стартует; журнал запросов только с шаблоном маршрута, без IP, ID, заголовков и тел (тест); `/health`; остановка по SIGTERM; настройки из окружения. Тесты с отдельной базой на тест (локально Postgres в Docker, в CI — сервис-контейнер; в CI без базы тесты падают, а не пропускаются). Заметки к деплою — docs/server.md
- [x] 3.2 Регистрация (идемпотентная: повтор с теми же ключами — 200, другие ключи — 409; код приглашения `STAYA_INVITE_CODE` только для новых аккаунтов), challenge → подпись с именем сервера → токен (в базе SHA-256, 30 дней, nonce сгорает при любой попытке), `Session` для остальных запросов, чистка просроченного. Коды ответов — protocol §4.1–4.2. Тесты на Postgres, включая регистрацию и вход настоящим ядром
- [x] 3.3 Каталог ключей (`server/src/keys.rs`): публикация с проверкой подписей сервером, лимит 100 OTK, выдача самого старого OTK ровно один раз (`FOR UPDATE SKIP LOCKED`), затем fallback; счётчик. Правила — protocol §4.3. Тесты: параллельные claim получают разные ключи, атомарный отказ при чужой подписи и переполнении, ключи настоящего ядра
- [x] 3.4 Ящики в PostgreSQL (`server/src/envelopes.rs`) по тем же правилам, что dev-сервер (`mailbox.rs`: размеры и причины отказа общие): upsert слота, очередь до ack (только своя), идемпотентное удаление своего слота, TTL 72 ч / 30 дней (не отдаются и удаляются), лимит очереди 200 при параллельных отправителях (все получатели запроса блокируются сразу в одном порядке — без взаимных блокировок), 256 конвертов на запрос. Тест на полноту списка миграций
- [x] 3.5 WebSocket `GET /v1/ws` (`server/src/live.rs`): события после коммита, только принятые конверты, номер управляющего сообщения совпадает с ящиком; до 4 соединений на аккаунт, ping 30 с, не дольше часа; подписки в памяти (один экземпляр сервера). Правила — protocol §8.2.6
- [x] 3.6 Лимиты частоты (`server/src/ratelimit.rs`, своя корзина токенов вместо tower-governor — без новых зависимостей): по IP на всё, строго по IP на регистрацию и вход, по сессии; IP только в памяти как солёный хеш, `X-Forwarded-For` — только при `STAYA_TRUST_PROXY=1`. Подробности — docs/server.md
- [x] 3.7 Сквозной тест (`tools/dev-peer/tests/e2e.rs`): два настоящих ядра регистрируются, входят, дружат (с ником) и обмениваются позициями через настоящий сервер и PostgreSQL; затем каждая строка каждой таблицы (текстом, bytea в hex) и журнал сервера на уровне debug проверяются на тестовые координаты во всех представлениях (строка, ×10⁷, f64/f32, оба порядка байтов) и на ник — 0 совпадений. Отдельный тест доказывает, что образцы находят координаты в настоящем открытом тексте пакета. Вместо `pg_dump` — выборка всех таблиц тем же подключением: работает и в CI без клиента Postgres
- [x] 3.8 Деплой сервера: образ `ghcr.io/realfamousbae/staya-server` из CI (только production-бинарник, проверка старта без базы), в compose `server` (loopback-порт, read-only, без capabilities, `STAYA_TRUST_PROXY=1`) и `postgres` 18 (внутренняя сеть, журнал без значений ключей); Caddy проксирует `/v1/*` и WebSocket; пароль базы и код приглашения генерируются на сервере; адрес и имя сервера — только из окружения (`STAYA_HOST`, `STAYA_DOMAIN`), в репозитории их больше нет. Проверено 04.10.2026: два настоящих ядра (`dev-peer --login`, через SSH-туннель к loopback-порту) зарегистрировались с кодом приглашения и обменялись позициями через развёрнутый сервер; в боевой базе и журналах сервера и Postgres тестовых координат нет; тестовые аккаунты удалены
- [x] 3.9 Карта Москвы и области со своего сервера: вырезка из ежедневной сборки Protomaps (`deploy/update-map.sh` → на сервере `go-pmtiles extract --bbox`, ~600 МБ, масштаб до 15), раздача `go-pmtiles serve` за Caddy (`/tiles/region.json`), стили light/dark с русскими подписями (`tools/map-style` → `deploy/map/style-*.json`, адрес подставляется при деплое), шрифты Noto Sans и спрайты из `protomaps/basemaps-assets` по закреплённому коммиту (`/map/*`). Сторонних запросов у карты нет
- [x] 3.10 Закрепление ключа: в приглашении до двух отпечатков (основной и запасной, `p=<a>.<b>`, protocol §5.3, включая правило для TOFU-клиентов), `reuse_private_keys` в Caddy, `deploy/pin.sh` и `deploy/backup-key.sh` (запасной ключ — только у владельца, в менеджере паролей), процедура смены ключа (docs/server.md); инструкция `docs/self-hosting.md`. Проверено 04.10.2026: после удаления сертификата Caddy получил у Let's Encrypt новый (другой серийный номер), а ключ и отпечаток остались прежними

Готово, когда: дамп базы не содержит ни одной координаты в открытом виде.

### Этап 4. MVP приложений

- [x] 4.1a Привязка к серверу в ядре (protocol §5.3): сервера по умолчанию в сборках нет — первый пользователь получает «ссылку на сервер» `staya://server?v=1&s=…&p=…`, остальные — сервер из приглашения; привязка (имя, отпечатки, ключ TOFU, токен сессии) — в зашифрованной базе ядра; аккаунт на одном сервере (`ServerMismatch`); правило доверия `check_server_key` (отпечатки или TOFU без молчаливой замены); помощники входа (`auth_challenge_request`, `auth_verify_request` с именем сервера без порта, `complete_login`, `session_token`); `create_invite` берёт сервер из привязки
- [x] 4.1b Android (`net/`): OkHttp; проверка ключа сервера в `HostnameVerifier` — после цепочки и имени, до первого байта запроса, одна для HTTP и WebSocket (`ServerKeyVerifier` → `check_server_key` ядра); `StayaClient`: вход через помощники ядра, 401 — повторный вход и один повтор, 404 на challenge — регистрация теми же ключами, 403 — нужен код приглашения, 429 без повторов; `Backoff` с разбросом и минимумом после 429; `LiveConnection` — WebSocket на экране: забор ящика при подключении, события по одному, переподключение, остановка при отвергнутом ключе. JVM-тесты с настоящим TLS (тестовый CA, MockWebServer) и настоящим ядром: основной и запасной отпечатки, при неверном ключе сервер не получает ни одного запроса (и по WebSocket), TOFU без замены, имя и цепочка проверяются до запоминания ключа, сценарии входа. Эмулятор в CI обменивается позициями через настоящий сервер с PostgreSQL и входом
- [x] 4.1c iOS (`ios/Staya/Net`): `URLSession`; `ServerTrustEvaluator` — цепочка для имени сервера, затем SHA-256 SPKI (берётся из DER сертификата — работает для любого типа ключа) в `check_server_key`; вызывается из делегата во время рукопожатия, до первого байта запроса, для HTTP (свой делегат на запрос — точное «ключ отвергнут») и WebSocket; `StayaClient` с тем же входом и повторами, что на Android; `LiveConnection` (actor) с `Backoff`. Правило доверия проверяется на Mac тестовыми сертификатами openssl (`scripts/test-ios-trust.sh`: отпечаток совпадает с openssl, неверное имя и цепочка не доходят до ядра); симулятор в CI обменивается позициями через настоящий сервер с PostgreSQL (Homebrew) и входом
- Подключение по IP с именем только для TLS — позже, если понадобится (iOS: ATS и SNI под вопросом; Caddy `default_sni` — с предупреждением пользователя)

2. Любое изменение протокола сначала оформляется в `docs/protocol.md`, потом в коде.
3. Правила для каждой сессии — в `CLAUDE.md`.
